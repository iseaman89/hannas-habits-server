# Design brief — Hanna's Habits

Written in roadmap step **M1** (2026-10-08) so later sessions read this file instead of re-importing the mockup.

- **Source:** claude.ai/design project "Hannas Habits UI-Redesign" (`a388ae78-c586-4176-a236-83ee88bef383`), file `Hannas Habits App.dc.html` (one interactive prototype with all screens), design system "Organic" (`_ds/organic-…/styles.css`, `readme.md`). Project last synced from the old frontend on 2026-10-07. `_ds_bundle.js` is empty (no components) and `support.js` is only the prototype runtime — neither carries design information. The project also holds `Hannas Habits.dc.html` and `Sidebar.dc.html` (recreations of the *old* screens, not read).
- **How it was read:** `DesignSync` read methods after `/design-login` (the `claude_design` MCP server itself was not configured in the session).
- The prototype is demo data + inline styles. It is a **visual reference, not code to copy**: rebuild it with Tailwind 4 tokens and typed components (F2+). Where it is wrong or incomplete, see "Gaps and deviations" below.

## 1. Design language ("Organic")

Warm, rounded, a little playful. Cream-and-sand ground, terracotta accent, sage second accent. Caprasimo display headings over Figtree body. Over-rounded containers, **pill** buttons/inputs/tags (`999px`), circles as the main shape (habit cells, mood buttons, resolution numbers, calendar days). Left-aligned layouts with air; no hairline-only geometry, no greys (warmth is the point). Icons: **Lucide, stroke-width 2.75**. Interactive states are themed (hover tint, pressed = one ramp step further, 2px accent `:focus-visible` ring) — never browser defaults. Disabled = 45 % opacity.

### 2.4 Type, space, radius, elevation

- **Fonts** (Google Fonts): `Caprasimo` 400 for headings/buttons/numbers, `Figtree` 400/600/700 for body. Base 15 px / 1.55. Headings: line-height 1.12, letter-spacing −0.015em. Page title (`h1`) 44 px; login hero up to 88 px; card titles 17–19 px; dialog title 26 px.
- **Kicker** above page titles: 12 px, uppercase, tracking 0.1em, bold, `accent-700`.
- **Space** (1.10× density): 4.4 / 8.8 / 13.2 / 17.6 / 26.4 / 35.2 px (`space-1,2,3,4,6,8`). The prototype mostly uses literal px (card padding 22–26, page padding 40/44, gaps 18/22/26) — round to the scale where it does not change the look.
- **Radius:** sm 8, md 16, lg 28; cards and dialogs `lg × 1.15 ≈ 32 px`; sidebar 32; buttons/inputs/tags/pills 999.
- **Shadow:** sm `0 1px 2px`, md `0 3px 10px`, lg `0 12px 32px` of `neutral-900` @ 14/16/22 %. Dark: black @ 40/45/55 %.
- **Theme:** `data-theme="light|dark"`, persisted in `localStorage['hh-theme']`, default light (the prototype ignores `prefers-color-scheme` — F2 may default to the system setting). `color-scheme: dark` in dark. Dark overrides: primary-button hover = `accent-400`; dialog backdrop black @ 55 %.

## 3. App shell and routes

Two-column layout, full viewport height: **sidebar** 240 px (floating `surface` panel, radius 32, 14 px outer margin) + scrolling `main` (padding 40/44).

Sidebar (top → bottom): logo (the notebook icon, the same for everybody - see §8 - + "*First name*'s Habits" in two lines; since 2026-10-09 the service carries the first name of whoever signed in last on this browser, "Hans' Habits" for a name ending in s, "Hanna" until anybody did) → nav pills **Today** (sun), **Habits** (list-checks), **Calendar** (calendar), **Resolutions** (target) — active = `accent` fill + `bg` text → *(spacer)* → light/dark segmented switch (sun / moon) → user card (initial avatar, **first name**, **email**, log-out icon button).

| Route | Screen | Nav item |
|---|---|---|
| `/login` (login + register as one screen with a mode toggle) | Auth | — |
| `/diary/:date` (`yyyy-MM-dd`); `/` redirects to today's date | Today / Daily diary | Today |
| `/habits` | Habit month tracker | Habits |
| `/calendar` | Year calendar | Calendar |
| `/resolutions` | Year resolutions | Resolutions |
| `/statistics?month=2026-10` (F15, not in the mockup) | Statistics of a month, per habit and part | Habits (no entry of its own; a "Statistics" button in the habits header carries the month) |

"Today" always jumps to the real today, also from a past diary day. "New habit" is a modal dialog over `/habits`, not a route.

## 4. Screens

All dates are the **client's local date** as `yyyy-MM-dd` (date-fns, never `toISOString()`); "today" is the client's, not the server's.

### 4.1 Auth (login / register)

Split screen: left a hero ("Hanna's Habits", tagline "Daily reflections, habits, and goals in one place.", three tags Daily diary / Habits / Resolutions) over decorative circles (terracotta-200, sage-200, a small sage-500 dot); right a card with the form. Light/dark switch top right.
- Login: Email, Password, **Log in**, divider "or", **Continue with Google**, link "New here? Create an account".
- Register adds two optional fields, **First name** and **Last name** (side by side; changed 2026-10-09, they were one "Your name"), and the button reads **Create account**.
- Needs from the API: `AuthResult` (exists) + **first/last name** (done, B5b; split into two fields on 2026-10-09).
- Not designed: field validation errors, 401 / 409 / 429 (lockout) messages, loading state, forgot password. Use the same pill inputs with the error text under the field and a form-level message from the ProblemDetails `title`/`detail`.

### 4.2 Today / daily diary (`/diary/:date`)

Header: kicker "Daily diary", `h1` = "Wednesday, 7 October", a **Saved** tag (sage, check icon), prev/next-day icon buttons. Next is disabled on today (no diary for the future).

Cards, in grid order:
1. **Greeting + Mood** — one card (changed twice on 2026-10-09: the user's wife did not like the page opening with a wide mood card; then greeting and mood were put together). One sentence in Caprasimo, "Hi, *first name*! How are you feeling today?" (on any other day than today "…How were you feeling on this day?"; 20 px, 26 px from a 32 rem card), and in the **same card** just the five faces — **no "Mood" title and no word for the chosen one** (a face's name is its tooltip and its accessible name). Faces: circle buttons (50 px on a wide screen, `clamp(2.25rem, 11vw, 3.125rem)` so that all five fit a 320 px phone) with Lucide faces `laugh`, `smile`, `meh`, `frown`, `annoyed`; selected = filled with the mood colour (`--hh-m*`), others `bg` with `neutral-700` icon. Radio-group semantics (`aria-label="Mood"`). **No clear button** (revised the same day, it had a reserved slot that pushed the faces off the middle): choosing the chosen face once more clears the mood (works with the space bar; the radio group says so to a screen reader, the chosen face's tooltip too). The faces share the card's width (`justify-between`: same room at both ends, so they are centred on a phone) and sit under the sentence; beside it (sentence left, faces right, ending at the card's padding) only where the card is ≥ 48 rem wide — a **container query** (`@3xl`), because the column is only ⅔ of the page and the viewport's width says little.
2. ~~**Body**~~ — **switched off in the UI (2026-10-09), not removed.** Big percentage (Caprasimo 22 px, sage) + slider 0–100, ends labelled **Drained** / **Energised**. `ScaleCard` is still in `features/diary`; to bring both cards back put them in `DiaryEditor` again.
3. ~~**Mind**~~ — switched off the same way; accent colour, ends **Foggy** / **Clear**. `body` and `mind` stay in the draft, the `PUT` and the API: a day that has them is saved with them (a test pins this), a new day sends `null`.
4. **Highlight of the day** — borderless textarea inside the card, placeholder "What made today worth remembering?".
5. **Grateful for** and **Something I learnt** — two cards, each a list of short lines with a coloured dot (sage / accent-400) and a last ghost row "Add something…" (inline add).
6. **Today's habits** (sage-200 card, right column) — habits **scheduled on the viewed weekday**: round check (28 px, filled sage when done / sage ring when open), title, flame icon + streak number; header link "N of M →" goes to `/habits`. Click toggles the record for the *viewed* date. (The streak shown is always the current streak as of the real today, not of the viewed day.)
7. **Tasks** — checklist (rounded-square checkbox 22 px, done = accent fill + strikethrough), counter "N done", input row "Add task and press Enter".

Header on a phone (below `sm`, since 2026-10-09): two rows — kicker "Daily diary" left with the **Saved** tag right, the date left with the previous/next-day buttons right. The same grid serves every screen (`PageHeader`); from `sm` the roomy layout as before.

There is **no save button**: the "Saved" tag implies **autosave** (F6: debounced write, one request in flight, status `saving… / saved / error`).

Data per day (document `PUT`): `mood` (1–5 or none), `body` 0–100, `mind` 0–100, `highlight`, `grateful[]`, `learned[]`, `tasks[{title, done}]`; plus habits-for-date (see §5).

### 4.3 Habits (`/habits`) — month tracker

Header: kicker "Habits", `h1` = "October 2026", primary button **+ New habit**. One card with a horizontally scrolling table (min-width ≈ 1060 px): header row = a column per day (pill with weekday letter + number, today highlighted in accent) and a "Streak" column; each habit = row with title, schedule label ("Every day", "Weekdays", "Weekends", else "Mon · Wed · Fri"), a trash icon button, 22 px circular day cells and a flame icon + streak number (Caprasimo 18 px).

Cell states: **done** (sage-500 fill + check) · **missed** (`--hh-miss` fill: scheduled, past, not done) · **due today** (2.5 px accent ring) · **future scheduled** (1.5 px neutral ring, not clickable) · **not scheduled** (small neutral dot, not clickable). Past and today cells toggle on click. Legend row below: Done / Missed / Due today / Not scheduled.

**New habit dialog:** title field ("What do you want to do?", placeholder "e.g. Stretch for 10 minutes"), seven round weekday toggles **M T W T F S S** (Monday first), preset tags **Every day / Weekdays / Weekends**, buttons Cancel and **Add habit · N×/week** (disabled without a title or without a day). UI index 0..6 = Mon..Sun ↔ API `(i + 1) % 7` (0 = Sunday).

**Repeat (F11, not in the mockup):** under the title a **Repeat** select - *On days of the week* (the toggles and presets above, plus "Every how many weeks?", 1 = every week) · *Every few days* ("Every how many days?", 2..365) · *A weekday of the month* (First … Last + weekday) · *A date of the month* (1st … 30th, **Last day** = 31). Rules that count from a day (every N weeks with N > 1, every N days) get a **Counted from** date, which follows the start date until a day is picked; a sentence under the picker says the rule in words ("Every 2nd week on Mon and Thu, starting with the week of Mon 5 Oct 2026"). The submit button keeps "· N×/week" only for a weekly rule that repeats every week. The line under a habit's name in the grid is the same rule in a few words ("Last Saturday of the month"). In the **edit** dialog a *changed* rule shows a note that it also applies to days that have passed (§9).

**A number of times a week / month (F13, not in the mockup):** two more kinds in the Repeat select - *A number of times a week* (1..7) and *A number of times a month* (1..28) - with one field "How many times a week?" / "…a month?" (the hint says: on whichever days; the week runs Monday to Sunday / the calendar month counts). No day is *due* for such a habit, so its cells have no "missed": an unticked past day and today are an **empty ring** (the same picture as a day to come, but tickable), a ticked day is the usual check. The line under the name reads "3 times a week · 2 of 3 this week" (the progress part only when the week of today is in the month on screen); in the Today panel the progress sits under the title ("2 of 3 this week", "3 of 3 in that week" for another day). The streak's flame is followed by a small "wk" / "mo": the streak counts weeks / months that reached the number. The submit button says "· 3×/week" / "· 8×/month". The grid legend gets "Not done (any day counts)" only while such a habit is on screen.

**Tags (F12, not in the mockup; taken out of the UI in F14, kept here for the day they come back - the parts below took their place):** under every day cell a small **dot** opens that day's tags - a filled terracotta dot when the day has tags (its name and tooltip list them), otherwise a ring that appears on hover / focus of the row (always, at 60 %, on a screen without hover). The cell's click stays "tick"; tags can go on any day (missed, not scheduled, before the start, to come). The dot opens a **dialog** "Tags for Wednesday 7 October": a field "Add a tag" (Enter), the day's tags as sage chips with ×, then suggestions as grey chips with their use count (the habit's own tags first) and a dashed accent chip "＋ Create “…”" for a name that does not exist. A day holds 10 tags; at 10 the field is replaced by a sentence. A "Manage tags" icon button in the header opens a second dialog: every tag with "Used on N days, last on …", rename (a name another tag has says "exists already - saving merges" and the button reads **Merge**), delete (confirms with how many days; the toast says how many it was taken off).

**Parts of a habit (F14, not in the mockup; the place the tag dot had):** a habit can have up to ten parts - "Legs" and "Arms" of "Sport" - each planned on some of the habit's own weekdays. Under every day on which at least one part is due the cell carries a small **"1/2"** (parts done / parts due; sage when all are done, neutral otherwise). It opens a **dialog** "Parts for Monday 5 October": the day's due parts as boxes (a day to come is read-only and says so; a part that is ticked there can still be taken back). The cell itself still ticks the whole day, which ticks every part that is due. The row has a "Parts of …" icon button (beside edit and delete) that opens a dialog "Parts of Sport": the parts with the days they are planned on, change (name + days) and remove (asks first: its ticks go with it, the habit's own days stay), "Add a part" (name + the round weekday toggles; only the habit's own days can be switched on; the shortcuts - Every day / Weekdays / Weekends - only for a habit that is on every day; a habit without parts opens straight on the form; at ten the button is replaced by a sentence). Every step there is saved at once. A part with a day the habit does not have any more says "Not due on Wed: the habit is not planned on that day any more." (or "Never due: …" when none of its days is left). The line under the habit's name ends with "· 2 parts"; the legend gets "1/2 - Parts done that day" only while a habit has parts. In the diary's Today card the day's due parts sit as small boxes under the habit.

### 4.5 Resolutions (`/resolutions`)

### 4.6 Statistics (`/statistics`, F15 — not in the mockup)

What was planned and done in a month, per habit and per part, and when each was last done. Header: kicker "Statistics", `h1` = "October 2026", previous / next month and "This month" like the habit grid; the month is `?month=2026-10`, the same address the grid uses, and the grid's header has a **Statistics** button that carries it (an icon on a phone). Body: one card per habit in creation order (a list, auto-fill columns of at least 22 rem): name, the rule in words, a big **share** ("82 %", a dash while nothing is judged), the count ("Done on 9 of 11 days" / "Reached the goal in 3 of 4 weeks"), a thin sage bar, and "Last done Sat 3 Oct · 8 days ago" / "Not done yet". ## 5. What the design needs from the API

Legend: **exists** · **change** (exists, needs a change) · **new**.

| Need (screen) | Status | Where |
|---|---|---|
| Register/login/Google/refresh/revoke, `AuthResult { user, tokens }` | exists | B5 |
| **First and last name** (register fields, sidebar, greeting, "Hanna's Habits"): `firstName` / `lastName` on `RegisterCommand` (both optional), from the Google `given_name` / `family_name` claims, in `AuthResult.user` (`{ id, userName, email, firstName, lastName }`; `firstName` is never empty - falls back to the email's local part -, `lastName` is `null` when none). Was one `displayName` until 2026-10-09; the migration `SplitDisplayName` splits an old name at its first word | done | **B5b** (split: PROGRESS 2026-10-09) |
| Habits CRUD, mark/unmark `PUT/DELETE …/records/{date}`; the weekdays were `schedule: number[]` (0 = Sunday) until B13, replaced by `recurrence` (next row) and **removed in B13b** | exists | B2/B4 |
| **Recurrence rules** (B13): `recurrence` is one flat object, `kind` says which of the other facts apply — `weekly` (`weekdays`, `interval` = every N weeks 1..52), `everyNDays` (`interval` 2..365, `anchor`), `monthlyOnWeekday` (`occurrence` first/second/third/fourth/last, `weekday`), `monthlyOnDate` (`dayOfMonth` 1..31; 29–31 fall on a shorter month's last day), and (**B15**, a *quota* with no due day) `timesPerWeek` (`times` 1..7 per calendar week) and `timesPerMonth` (`times` 1..28 per calendar month; 28 so that February can reach it). Weeks start on Monday. `anchor` (yyyy-MM-dd) is the day the rhythm counts from (every N weeks with N > 1, every N days); it is *part of the rule*, not the start date, so moving the start date never shifts the rhythm — a client sends the anchor it got back; omitted = the start date as saved. Answers: `recurrence` in create/list/details/overview (all facts present, the unused ones `null`/`[]`); requests: `recurrence` is optional on create (omitted = every day) and **required on update** (400 `errors.recurrence`; an update replaces the whole habit). The former weekday list `schedule` is gone (**B13b**): answers do not carry it and a request that still sends it is read as if it had not (create: every day; update: 400). | done | **B13**, B13b, B15 |
| Habits **overview** in one call for the month grid and the Today panel: `GET /api/habits/overview?from=&to=&asOf=` → `[{ id, title, recurrence, startDate, scheduledDates[], completedDates[], taggedDays[], quotaPeriods[], currentStreak, subHabits[] }]`. Grid: `from/to` = month; Today panel: `from = to = viewed date`. `scheduledDates` (B13) = the days of `from..to` the habit is due on — the rule applied and none before `startDate`; a client no longer derives "not scheduled" from weekdays. **Quota habits (B15):** every day from `startDate` is in `scheduledDates` ("can be ticked" — no day is *due*, so a client must not paint an open past day as missed), and `quotaPeriods: [{ from, to, done }]` lists every week/month that touches `from..to` (oldest first, a period that ended before `startDate` is left out, one that has not begun is `done: 0`); `from`/`to` are the whole period, `done` counts completed days of the *whole* period from `startDate` on and up to `asOf` (so a week that reaches out of the grid's month shows its true number); the aim is `recurrence.times`. Empty `[]` for every other rule. One query instead of 1 + N requests; streak must be server-side because it can span months. `from`/`to` required, at most 366 days apart (B13), `asOf` optional (default = server UTC date). | done | **B8**, B13 |
| **Current streak** (pure domain logic): walk back from `asOf` over *scheduled* days only; unscheduled days neither count nor break; `asOf` itself counts if done and is ignored (not a break) if still open; the first earlier scheduled day that is not done ends the streak; stop at `startDate`. Records after `asOf` and on unscheduled days are ignored. **Quota rules (B15) count periods, not days:** the weeks (Monday–Sunday) or calendar months in a row that reached `times`, back from the period containing `asOf`; that one counts if it has reached `times` and is skipped (not a break) while it is still running; the first earlier period that fell short ends the streak; the period of `startDate` is the oldest one and counts only if it reached `times` with the days from the start on. The number is in weeks (`timesPerWeek`) or months (`timesPerMonth`) — the client says the unit. | done | **B8**, B15 |
| **Habit `startDate`** (`DateOnly`): the prototype draws every scheduled past day of a *new* habit as "missed". Cells before `startDate` must render as not-applicable, and streak/stats must stop there. `EntityBase.CreatedAt` is a UTC timestamp and can be off by a day in the user's local date, so use an explicit date (client sends it, default = server UTC date; optional on create; range 2000-01-01..2100-12-31; editable since B12: optional on `PUT`, omitted = unchanged, so earlier days can be back-filled). | done | **B8** |
| Daily diary as one document per user+date: `GET/PUT/DELETE /api/daily-diaries/{date}`; fields `mood` (1–5, nullable), `body`/`mind` (0–100, nullable), `highlight` (nullable), `grateful[]`, `learned[]`, `tasks[{title, done}]`. Replaces `Text` (required) — an entry may now consist of just a mood. | done | **B6** |

- **Quota rules (decided in B15 / F13).**
  - **The week is Monday to Sunday and the month is the calendar month** (rolling windows - "3 in any 7 days" - were not built: nobody counts like that). A week that spans two months is one week; its progress is counted over the whole week, also where it leaves the grid's month (`quotaPeriods` is server-side for exactly this reason).
  - **Streak:** periods in a row that reached the number, back from the running one. The running period counts when it has reached it and is *skipped* (not a break) while it is still open, like today's open cell in the day streak; it is not broken early when it can no longer be reached - it is judged when it is over. The period the habit started in counts only if it reached the number with the days from the start on (a Friday start with 5 a week simply cannot count that week - there is no proration; it is the oldest period, so it never costs a streak, it only may not add one).
  - **Limits:** 1..7 a week (7 is not "daily": the streak counts weeks) and 1..28 a month (so February can reach it).
  - **A day of a quota habit is "scheduled" for the client** (it can be ticked) but never "due"; the client must not paint an open day as missed (`cellState({ quota })` → `open`). The alternative - an empty `scheduledDates` and a new "may be ticked" list - was rejected: the answer would need a second list that says the same as the first for every other kind.
  - **Not built:** a marker for a *past* week that was met or missed (the ticks show it, and the streak says how many in a row), a per-week target that changes over time (the rule has no history, §9), "at most N" quotas.

- **Sub-habits (decided in F14).**

The habit form has a Save button, the parts are saved step by step - two ways of saving in one dialog is a trap (Cancel would not undo an added part); the part's own add/change form would sit *inside* the habit's `<form>` (invalid HTML, Enter would submit the wrong one); and the days a part may choose come from the habit's **saved** rule, not from a half-edited one in the same dialog. The dialog is the shape the tags had and keeps the grid as it is; the alternative stays open if parts turn out to be the main thing.
  - **The cache mirrors the server's cascade** (a habit's tick ticks the due parts, the last due part completes the day, ...) so the screen answers at once. It is a copy of a server rule on the client - checked against the real API, repaired by the refetch after the last pending mark - and the one place where the client knows "due" in any way: it looks the per-part `scheduledDates` up, it never works the weekday rule out.

- **Statistics (decided in B17 / F15).**
  - **Scope:** per habit and month: planned vs. done, "last done", and the same for each part — the three things of the roadmap line. **Not built:** a longest streak, a per-weekday breakdown, a year view, a trend over months, charts of any kind, tag statistics (the tags stay unused), a statistic across habits (units differ: days / weeks / months, a sum would mean nothing).
  - **One endpoint with `from/to/asOf`, not `month=`:** the same three values as the overview, so a quarter or a year is the same call later (≤ 366 days); the screen asks for a month.
  - **Judging "today":** an open today is not a miss (the streak's principle) — the share would otherwise drop every morning and recover by the evening. A done today counts at once.
  - **A quota counts periods, and a period belongs to the month it *ends* in:** every week is counted exactly once over consecutive months, and it is judged when it is over. Consequence: the first days of a month can carry a week whose ticks lie in the month before. A running period counts only once it has reached its number (the streak's rule: skipped while open).
  - **The period the habit began in is not judged** (the streak counts it when it was reached). Counting a Friday start's partial week as a miss would punish the person for starting; counting it only when met would bias the share up. The streak may therefore be one longer than the statistic suggests, by that week.
  - **Marks on days that were not due are ignored** (as for the streak) — so the share never exceeds 100 %, and "extra" days are invisible here. `lastDoneOn` does include them: it is a fact about the person, not about the plan.
  - **The rule history is not modelled** (§9): a changed rule re-judges the whole past, also here.
  - **No nav entry, a button in the habits header** (the bottom bar has four tabs at 320 px; "Resolutions" at 12 px already takes ~66 of the 80 px a tab has). The sidebar still marks Habits as current on `/statistics`. Not looked at in a browser, as the rest.
  - **The share's rounding never lies:** 199 of 200 is 99 %, 1 of 300 is 1 %; nothing judged is a dash, not "0 %".

- Interactive `div`/`span` with `onClick` everywhere → real `button`s / `role="radio"` / `role="checkbox"` / `<input type="range">` with labels and keyboard support (the old UI had clickable `<img>`s — F9 lists this too).
- Inline styles and hard-coded demo data, `localStorage` only for the theme, "carry" streak offset (demo seed), fake login that accepts anything.
- The habit streak and the Today panel's "N of M" are computed in the prototype from local state; in the app they come from the overview query.

## 9. Known limitation worth stating

The schedule has no history: if a habit's schedule is edited, past cells are re-judged with the *new* schedule (missed/not-scheduled and the streak change retroactively; records on days that are no longer scheduled are kept but hidden and not counted). Modelling schedule versions would be over-engineering for this app; revisit only if it annoys in practice. The same holds for a moved start date and for a changed recurrence rule (B13): the edit dialog says so for a changed rule (F11).
